# 영어 회화 평가 서비스 구현 로드맵

작성일: 2026-10-13.

## 1. 목표와 범위

**2일 안에 사용자가 AI와 음성으로 대화하고, 영어 회화 평가 보고서를 받는 흐름을 완성한다.** 평가 세션 일시정지·재개와 AI 분석 재시도를 포함한다. 회원가입·로그인·본인 평가 기록 조회도 현재 기능 명세에 따라 구현한다.

기준 문서는 [기능 명세](../product/feature_list.md), [PRD](../product/PRD.md), [아키텍처](./architecture.md), [정규화 ERD](./erd.md), [DBML](./erd.dbml)이다. 이 로드맵은 구현 순서를 정하며 기존 기능이나 ERD를 임의로 삭제하지 않는다.

Refresh Token 발급·갱신·폐기와 갱신 시 해시 교체는 구현 범위에 포함한다. 네트워크 연결 복구, 별도 서버 로그인 세션·기기 관리·토큰 회전 이력·재사용 탐지, 감사 로그, 운영 모니터링, 약관·동의 기능은 제외한다. 평가 세션 재개는 저장된 진행 지점을 이어가는 제품 기능으로 구현한다.

## 2. 현재 출발점

| 영역 | 확인된 상태 | 필요한 작업 |
| --- | --- | --- |
| 모노레포 | React·NestJS·Turborepo·pnpm 및 `@root/*` 패키지 구성 존재 | 실제 기능 모듈과 빌드 연결 |
| tRPC | 헬스 체크가 tRPC → Controller로 연결됨 | 인증·평가·보고서 계약 확장 |
| React | 시작 화면과 API 연결 표시 존재 | 녹음·대화·보고서·재개 화면 |
| Prisma | generator와 datasource만 존재, 모델 없음 | ERD 모델·제약·마이그레이션·시드 |
| 외부 환경 | PostgreSQL·Redis·MinIO Compose 구성 존재 | 로컬 실행 확인 및 어댑터 연결 |
| AI 처리 | 구현 없음 | 음성 인식·질문 생성·TTS·평가 연동 |

설정 파일이 있다는 사실과 실제 실행 검증이 끝났다는 사실을 구분한다. 환경 실행과 실제 AI 요청 성공은 1단계에서 확인한다.

## 3. 구현 순서와 시간 배분

아래 시간은 하루 8시간, 총 16시간의 집중 구현을 가정한 작업 배분이다. 인원과 실제 외부 연동 난이도에 따라 조정한다. FE와 BE를 단계마다 함께 연결하고, 실제 동작으로 완료 여부를 확인한다.

| 일차 | 단계 | 배분 | 구현 내용 | 완료 기준 |
| --- | --- | --- | --- | --- |
| 1일차 | 1. 실행 환경·계약 확정 | 1시간 | 로컬 환경 실행, 음성 전달 방식과 AI 입출력 확인 | 브라우저에서 WAS 호출, DB·MinIO 접근 및 실제 AI 요청 성공 |
| 1일차 | 2. 음성 한 사이클 검증 | 1시간 | 녹음 → 전사 → AI 질문 → TTS 재생 최소 연결 | 사용자가 녹음한 답변에 대한 AI 음성을 브라우저에서 재생 |
| 1일차 | 3. 저장 모델·인증 | 2시간 | Prisma 모델·마이그레이션·시드, Access JWT 로그인·Refresh Token 갱신 | 회원가입·로그인 후 본인 평가 세션 생성 및 토큰 갱신 가능 |
| 1일차 | 4. 저장되는 회화 흐름 | 4시간 | 첫 질문, 음성 저장·전사, 답변 분석, 후속 질문, 상태 조회 | 실제 AI와 여러 턴 대화하고 질문·답변·음성 참조가 DB에 저장됨 |
| 2일차 | 5. 최종 평가 | 3시간 | 종료 조건, 최종 분석, 항목별 결과·근거·피드백 저장 | 종료한 평가에서 5개 항목과 최종 수준이 포함된 보고서 생성 |
| 2일차 | 6. 세션 재개·재시도 | 2시간 | 일시정지·재개, 분석 실패 재시도 | 저장된 질문부터 이어가기 및 실패 분석의 제한된 재실행 성공 |
| 2일차 | 7. 보고서·기록 화면 | 1시간 | 보고서 조회, 평가 기록, 상태별 안내 | 사용자가 본인 결과를 조회하고 일시정지 평가를 찾아 재개 |
| 2일차 | 8. 통합 검증·시연 | 2시간 | 핵심 시나리오 검증, 오류 수정, 시연 동선 정리 | 실제 음성 평가를 처음부터 보고서까지 완료 |

**1일차 종료 기준은 DB에 저장되는 실제 음성 대화다. 2일차 종료 기준은 평가 보고서, 세션 재개, 분석 재시도를 포함한 전체 흐름이다.**

## 4. 단계별 작업

### 1단계 — 실행 환경과 경계 계약

- [ ] 웹·API와 PostgreSQL·Redis·MinIO를 로컬에서 실행한다.
- [ ] 기존 `build`, `typecheck`, Prisma 검증 명령이 실행되는지 확인한다.
- [ ] 서버에서 사용하는 AI 인증 정보와 음성 저장 설정을 준비한다.
- [ ] 녹음 형식, WAS로 음성을 전달하는 방식, AI 음성을 재생하는 참조 형식을 확정한다. 실제 사용 중인 tRPC 어댑터에서 음성 요청이 가능한지 샘플로 확인한다.
- [ ] 평가 설정·질문·답변·진행 상태·보고서의 입력 및 출력 타입을 정의한다.
- [ ] 최대 평가 시간, 재개 허용 시간, 최초 실행을 포함한 재시도 한도, 점수 범위를 정한다. 현재 문서에서 미확정인 값을 구현 전에 설정·시드로 명시한다.

특히 다음 AI 입출력은 샘플 응답으로 먼저 확인한다.

| 작업 | 입력 | 필요한 결과 |
| --- | --- | --- |
| 음성 인식 | 사용자 답변 음성 | 전사문, 지원되는 경우 구간별 시작·종료 시각과 신뢰도 |
| 질문 생성 | 주제, 시작 수준 또는 관측 결과, 이전 대화 | 질문 텍스트, 난이도, 평가 의도 |
| TTS | 확정 질문 텍스트 | 브라우저에서 재생 가능한 음성 |
| 회화 평가 | 질문·답변·전사 및 필요한 원본 음성 | 항목별 판단, 실제 발화 근거, 최종 수준·피드백 |

전사문만으로 발음 평가가 가능하다고 가정하지 않는다. 원본 음성을 평가 입력으로 사용하는 경로와 음성 구간 참조를 확인한다. AI 응답에 없는 신뢰도·시간 구간은 임의로 만들어 저장하지 않는다. 필요한 정보가 제공되지 않으면 지원되는 연동 방식이나 실제 음성 처리 방법을 먼저 확정한다.

### 2단계 — 녹음부터 AI 음성까지

- [ ] React에서 마이크 권한 요청, 녹음 시작·종료, 보내기 버튼을 구현한다.
- [ ] 녹음한 데이터를 WAS에 전달하고 실제 AI 전사 결과를 받는다.
- [ ] 답변을 맥락으로 후속 질문을 생성하고 TTS 음성을 재생한다.
- [ ] 녹음 중·전송 중·AI 처리 중·재생 중 상태를 화면에 표시한다.

이 단계는 외부 연동 가능성을 확인하는 최소 흐름이다. 임시 데이터로 검증하더라도 4단계 완료 시점에는 저장소와 내부 포트로 연결한다. 최종 시연은 실제 AI 응답을 사용한다.

### 3단계 — 정규화된 저장 모델과 회원 인증

회원 인증의 계약, 저장 구조, 계층별 책임, 검증 시나리오는 [회원 인증 구현 계획](./auth_implementation_plan.md)을 따른다.

- [ ] DBML의 모델과 ENUM을 Prisma 스키마로 옮긴다.
- [ ] PK·UNIQUE·FK와 필요한 CHECK 제약을 마이그레이션에 반영한다. Prisma 스키마에서 표현되지 않는 제약은 마이그레이션 SQL로 관리한다.
- [ ] 주제, 평가 정책, 5개 항목과 9개 수준의 평가 기준을 시드로 준비한다.
- [ ] 회원가입·비밀번호 해시·로그인·Access JWT 검증·회원 조회를 구현한다.
- [ ] Refresh Token 난수 발급·해시 저장·쿠키 전달·만료 검증·원자적 해시 교체를 통한 auth.refresh를 구현한다.
- [ ] Refresh Token 폐기와 쿠키·클라이언트 Access Token 삭제 방식의 로그아웃을 연결한다.
- [ ] 만료·폐기·무효 토큰 및 비활성 회원의 갱신 거절, 동시 갱신 중 단일 성공, 로그아웃 후 갱신 거절을 검증한다.
- [ ] 인증된 사용자의 평가 세션 생성과 소유권 검증을 구현한다.

DB 결과를 편의상 JSON·배열 컬럼에 몰아넣거나 집계값을 중복 저장하지 않는다. 작업 상태와 시도 수는 ERD에 정의된 사실에서 계산한다. 기준·모델 버전은 현재 ERD를 구현하되, 별도 관리 화면이나 운영 이력 조회 기능은 추가하지 않는다.

### 4단계 — 저장되는 회화 흐름

- [ ] 주제·시작 수준 조회와 선택 화면을 연결한다.
- [ ] 평가 시작 시 첫 질문 생성·TTS·음성 참조 저장을 연결한다.
- [ ] 답변 음성을 MinIO에 저장하고 `audio_asset`·`answer`를 연결한다.
- [ ] STT 결과를 `transcript_segment`에 저장하고 사용할 전사 결과를 확정한다.
- [ ] 답변별 평가 관측과 근거 구간을 저장한다.
- [ ] 대화 맥락과 관측 결과에 따라 다음 질문을 생성한다.
- [ ] 현재 질문, 답변 처리 상태, 평가 상태를 조회해 화면에 표시한다.
- [ ] 답변 전송·처리 중에는 추가 제출을 막고, 질문당 답변 하나라는 규칙을 검증한다.

원본 음성은 발음·유창성 분석 입력으로 유지한다. 전사 구간은 STT 결과이고, `audio_span`은 평가 근거가 가리키는 음성 위치라는 역할을 구분한다. 상세 데이터 경계는 [음성 시퀀스](./voice-assessment-sequence.html)를 따른다.

### 5단계 — 종료와 최종 평가

- [ ] 사용자 종료, 최대 평가 시간, 충분한 평가 근거에 따른 종료를 구현한다.
- [ ] 종료 후 새 답변을 차단하고 이미 접수된 답변 처리를 마친다.
- [ ] 같은 평가의 질문·답변·전사·원본 음성 근거를 모아 최종 분석한다.
- [ ] 어휘·문법·발음·유창성·답변 적절성의 5개 결과와 9개 수준 중 최종 판단을 검증한다.
- [ ] 실제 답변과 음성 구간을 참조하는 근거, 개선 사항을 저장한다.
- [ ] 데이터 부족은 0점 대신 항목별 데이터 부족으로 표시한다. 확정·잠정·평가 불가 판정과 기술적 분석 실패를 구분한다.
- [ ] 결과 저장을 완료한 평가만 보고서 조회 대상으로 반환한다.

### 6단계 — 세션 재개와 분석 재시도

**세션 재개**

- [ ] 사용자의 일시정지 요청에 따라 진행 지점을 저장한다.
- [ ] 답변 처리 중 일시정지 요청은 접수된 답변 결과를 확정한 뒤 적용한다. 질문·답변의 저장 지점이 불분명한 상태로 재개하지 않는다.
- [ ] 본인 평가의 상태와 재개 허용 시간을 확인하고 마지막 확정 질문·답변부터 이어간다.
- [ ] 이미 답변한 질문을 다시 제출하지 않고 다음 진행 지점을 반환한다. 아직 답변하지 않은 질문은 기존 질문을 반환한다.
- [ ] 재개 허용 시간을 넘기면 기존 종료 규칙에 따라 처리한다.

재개 대상은 서버에 저장된 평가 진행 상태다. 브라우저에만 있던 미제출 녹음이나 끊긴 요청을 복원하는 네트워크 복구 기능은 포함하지 않는다.

**분석 재시도**

- [ ] 실패한 분석의 같은 입력을 사용해 정해진 횟수 안에서 재실행한다.
- [ ] `ai_attempt`로 시도를 구분하고 성공한 결과 하나를 채택한다. 시도 수 집계 컬럼은 추가하지 않는다.
- [ ] 결과 형식 오류 등 재시도 가능 여부와 최대 횟수를 확인한다.
- [ ] 이미 완성된 보고서를 재시도로 중복 저장하지 않는다.
- [ ] 모든 시도가 실패하면 분석 실패 상태를 화면에 표시한다.

분석 재시도 실행은 Redis/BullMQ 어댑터에서 연결한다. 작업 관리 대시보드나 별도 재시도 이력 화면은 만들지 않는다.

### 7단계 — 보고서와 평가 기록

- [ ] 최종 수준, 5개 항목별 결과, 판단 근거, 개선 피드백을 표시한다.
- [ ] 데이터 부족·잠정·평가 불가를 사용자가 구분할 수 있게 표시한다.
- [ ] 본인 평가 기록에서 주제·일시·상태·최종 수준을 조회한다.
- [ ] 일시정지 평가에 재개 진입점을 제공한다.
- [ ] 평가 중에는 힌트·표현 교정·추가 설명을 제공하지 않고, 개선 피드백은 종료 후 보고서에서 제공한다.

## 5. 코드 구성 원칙

BE는 회원, 평가 진행, 보고서 기능 단위로 NestJS 모듈을 구성한다. 음성 저장과 AI 처리는 해당 유스케이스의 아웃바운드 포트로 연결한다. 테이블마다 Controller·Service를 하나씩 만들지 않는다.

```text
React
  → tRPC Procedure
  → NestJS Controller
  → Inbound Port
  → Application Service
  → Domain / Outbound Port
                  ↑
           Outbound Adapter
```

위 마지막 화살표는 어댑터가 포트를 구현한다는 코드 의존성을 나타낸다. 실제 외부 호출은 Application Service가 포트를 통해 어댑터에 위임한다.

- 내부 영역은 유스케이스·비즈니스 규칙·포트와 계약을 소유한다.
- Controller는 입력·출력 변환과 인바운드 포트 호출을 담당한다.
- tRPC의 형식 검증·JWT 검증은 인바운드 어댑터에서 실행한다. 일반 함수로 호출한 Controller에 NestJS Guard·Pipe가 자동 적용된다고 가정하지 않는다.
- Domain은 평가 상태 전이, 답변 접수, 종료·재개 조건을 담당한다.
- Prisma·AI SDK·MinIO·BullMQ 타입을 내부 공개 계약이나 React 응답에 노출하지 않는다.
- React는 현재 FSD 방침에 따라 인증, 평가 설정, 녹음·대화, 보고서·기록 기능을 구성한다. 기능 구현에 필요한 공통 UI부터 추출한다.

## 6. 완료 검증

각 단계에서 기존 `corepack pnpm typecheck`와 `corepack pnpm build`를 확인한다. 저장 모델 변경 시 `corepack pnpm db:validate`와 실제 PostgreSQL 마이그레이션을 검증한다. 테스트는 주요 비즈니스 규칙과 데이터 경계를 중심으로 작성한다.

| 검증 시나리오 | 확인할 결과 |
| --- | --- |
| 정상 평가 | 가입·로그인 → 주제 선택 → 실제 음성 대화 → 종료 → 보고서 조회 |
| 평가 재개 | 일시정지 → 화면 재진입 → 마지막 저장된 지점에서 이어가기 |
| 분석 재시도 | AI 어댑터의 첫 실행만 의도적으로 실패시킴 → 다음 실행 성공 → 보고서 하나 저장 |
| 재시도 한도 | 계속 실패시킴 → 정해진 횟수에서 중단 → 분석 실패 상태 |
| 소유권 | 다른 사용자의 평가 진행·재개·보고서 접근 거절 |
| 종료 상태 | 종료 후 답변 접수와 평가 재개 거절 |
| 평가 데이터 부족 | 0점으로 대체하지 않고 부족 사유와 판정 표시 |
| 근거 연결 | 보고서 근거가 해당 평가의 실제 답변과 유효한 음성 구간을 참조 |

상태 전이와 재시도 한도는 빠른 단위 테스트로, Prisma 관계·보고서 저장은 DB 통합 검증으로 확인한다. 최종 시연은 브라우저에서 실제 마이크·AI·음성 재생을 사용한다.

## 7. 일정 점검 지점

1. **2시간 시점:** 실제 음성 한 사이클이 동작해야 한다. 음성 형식·AI 평가 입력 문제가 있으면 저장 모델과 화면 작업을 늘리기 전에 해결한다.
2. **1일차 종료:** 여러 턴 대화와 영속 저장이 동작해야 한다. 인증·DB·AI 연동이 각각 따로 동작하는 상태로 종료하지 않는다.
3. **2일차 중반:** 보고서 생성이 동작해야 한다. 이후 시간은 세션 재개·재시도·전체 시연 검증에 배분한다.
4. **시연 2시간 전:** 새 기능 추가를 멈추고 정상 흐름, 세션 재개, 재시도 시나리오를 확인한다.

일정이 밀리면 화면 장식, 주제·예시 데이터의 개수, 독립된 관리 화면을 줄인다. 세션 재개·분석 재시도·5개 평가 항목·정규화 원칙은 합의한 구현 범위로 유지한다.
